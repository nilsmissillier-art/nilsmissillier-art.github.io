With residential solar on the rise, a household with solar panels constantly faces the same trade-off: when should it run the washing machine, charge the electric car, or fill the home battery so it uses its own solar power rather than drawing from the grid? HeliosOpt is a project management course project at Centrale Lille (G1/G2 project), carried out by a team of 8, whose goal is to build an open-source web / Android app that answers this question automatically.

8 Team members
3 Audits (Dec. 2026, June 2027, Feb. 2028)
7 Weather / solar APIs compared
100% Open source

01 — Goal

Starting from the specifications of the installation (peak power, orientation, tilt, battery, electric vehicle, flexible appliances), the app forecasts solar production using weather APIs. A constrained optimization engine then builds the ideal hourly schedule for each appliance to maximize the self-consumption rate. The result is shown to the user as a dashboard of daily recommendations.

02 — Where the project stands

We are in the definition phase: review of existing apps, SWOT analysis, project charter and objectives matrix. We compared seven data sources (Open-Meteo, Météo-France AROME, Solcast, Forecast.Solar, Meteoblue, OpenWeatherMap, WeatherAPI) on coverage, cost, quotas and privacy, and defined the processing pipeline: weather API → production estimate with pvlib → comparison with real inverter measurements. This work is coordinated with OptiGrid, a related project.

03 — Next steps

Technical specifications for the December 2026 audit, a first prototype validating the APIs and the optimization algorithm in early 2027, then a finished, documented web app released under an open-source license by February 2028.

As part of the Start & Go Robotics module at Centrale Lille, our team of 8 designed a robot able to locate a sheet of paper placed in front of it, then draw an image on it from an .rle file. The project covered the whole chain: mechanics, sensors, actuators, control engineering and embedded software.

8 Team members
6 Weeks of project work
3 Dynamixel motors
≈€250 In hardware

01 — Design

We compared two architectures: a rail-based, printer-style robot and an articulated arm. The rail-based robot suffered from friction, took up a lot of space on the drawing surface and was slow. We therefore chose a SCARA-type arm: two arms with pivot joints and a slide to raise and lower the pen, driven by 3 Dynamixel XL330 motors. The robot was modeled in Onshape and built at the fablab (3D-printed parts, laser-cut wooden gears).

02 — Sensors & software

To find the sheet, the robot performs a circular sweep with a single RGB sensor. Otsu thresholding separates the sheet from the background, and the centroid of the detected points gives its center, whatever the sheet's orientation. The embedded code on an Arduino Mega is built as a state machine and communicates with both the PC and the motors. It decodes .rle files, keeping only the contours to cut drawing time, and controls the arm using inverse kinematics, the Jacobian matrix and a PI controller, all validated first in simulation on a PC.

03 — Results

Against the initial specifications, sheet detection, raising and lowering the pen, and .rle file conversion all work. 3D modeling, the pivot joints, drawing around the center and contour tracing were only partly achieved. Moving in a straight line from point A to point B and precisely locating the center could not be validated on the real robot. The main obstacles were the gap between the theoretical model and reality, and the time spent on design and reprinting parts. Above all, this project taught me the value of breaking work into small chunks, testing intermediate parts rather than building everything at once, and coordinating closely between the different sub-teams.

Presentation slides (in French):

How can weather data be used to estimate avalanche risk on the European 1-to-5 danger scale? That's the question behind my TIPE (a supervised independent research project required in French preparatory classes for engineering schools), completed during my CPGE MPI track — a topic that ties naturally into my training as a ski instructor.

2 Models compared
≈99% Accuracy within ±1 risk level
≈58% Exact accuracy (no tolerance)
100% C Algorithms built from scratch

01 — Data

Cleaning of snow and weather records from Météo-France, followed by non-parametric feature selection (mutual information, mRMR criterion) to narrow dozens of raw descriptors down to the handful that are genuinely predictive: snow depth, precipitation, grain type, temperature, and daily weather conditions.

02 — Models

Two approaches are implemented entirely in C, with no machine learning library: a Poisson regression (GLM) fitted with the Newton-Raphson method (the IRLS algorithm), and a Random Forest built tree by tree, using Gaussian elimination to solve the underlying linear systems. Data preprocessing is handled in Python.

03 — Results

On the test set, both models reach close to 99% accuracy when allowing a one-level tolerance (±1) on the risk scale, with the Random Forest holding a slight edge in root-mean-square error. I want to be upfront about what that number hides, though: exact accuracy — predicting the precise level, with no tolerance — sits closer to 58%. That gap says less about the models failing than about how compressed the 1-to-5 scale is and how rare the most severe levels are in the data, but it's the honest number, and I'd rather present it than let ±1 accuracy speak alone. The rarer, most severe risk levels (4-5) remain the main limitation for both approaches — a structural limitation I discuss openly rather than a flaw to hide.
